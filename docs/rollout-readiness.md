# v1.0 Rollout Readiness

## Completed for `v1.0.0`

- One physical `skill/` product boundary with no core registry path outside it.
- Product-only skill-pack archive validated through bootstrap and project validation.
- Five or six recurring documents instead of RC.1's seventeen.
- Operational-contract validation for workflows, standards, gates, and policies.
- Controlled project-record validation for roadmap, milestone, next-step, task, impact,
  evidence, invariants, acceptance, status, journal, reports, decisions, waivers, and registers.
- Three executable consuming-project cases covering feature, bug-fix, and refactoring.
- Python and C++ ecosystems with Codex, Claude, and Cursor delivery paths.
- Frozen CLI, schema, profile, adapter, runtime, and operating-system contracts.
- Ten-minute recommended adoption path.
- All frozen console entry points exercised from the built wheel in the available Linux
  environment.

## Measured RC.4 evidence

- Route accuracy and required-document recall: 100%.
- Missed acceptance gates: 0.
- Maximum recurring documents: 6.
- Average selected context: approximately 3,829 tokens.
- Reduction from RC.1 selected context: 20.65%.
- All rollout cases pass with the consolidated context and stricter project validation.
- Ordinary selected context stays at six documents; structural records and their contract
  are project-owned or conditional rather than always-loaded guidance.

## External constraints

- No public Git remote is configured, so the hosted operating-system and Python matrix
  has not executed.
- No authorised signing key is configured.
- Independent vendor-model runs were unavailable; local tests exercise their adapter
  contracts and project files.

These constraints prevent representing the release as a signed public release. They do not
block internal rollout of reproducible local artefacts.

## Stable-release maintenance rule

Treat destructive behaviour, broken installation or migration, composition drift, public-contract
defects, and adoption instructions that do not work as release blockers. Optional improvements are
follow-up work.

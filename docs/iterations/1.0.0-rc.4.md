# Iteration 1.0.0-rc.4: Structural Execution Contracts

## Why this was the highest-priority next step

The shared workflows and language standards were operational, but agents could still omit high-impact risk categories, overstate validation, and lose architectural invariants. These omissions have a higher correctness cost than their small recurring token cost.

## Scope

- Complete engineering standards for Python, Rust, C++, Dart/Flutter, q/kdb+, and TypeScript.
- Cross-language public API documentation requirements.
- General design principles including responsibility, cohesion, coupling, dependency direction, encapsulation, DRY, YAGNI, and KISS.
- Controlled change-impact, evidence-manifest, and invariant records.
- Explicit required outputs for every workflow.
- Project-record authority hierarchy and deterministic test tiers.
- Product and maintainer usage documentation.
- Public-release readiness checklist.

## Exclusions

- No new development workflow family.
- No automatic planning or autonomous repository mutation.
- No public plugin distribution or external trust infrastructure.

## Acceptance

- All workflow definitions declare outputs.
- Operational impact records reject unknown values and missing activated gates.
- Final evidence records reject unsupported pass claims.
- Active invariants require stable IDs, enforcement, and review triggers.
- Standard bootstrap creates all three structural records.
- Normal context remains within the eight-document and 20% RC.1-reduction guards.
- Rollout and release artefacts validate from the exact candidate tag.

## Internal-testing readiness

The repository remains credible for internal rollout: it has a runnable package, product-only skill pack, passing core smoke workflows, controlled migration, and no known blocking data-loss issue. Public readiness still requires remote CI and independent adoption evidence listed in `docs/public-release-readiness.md`.

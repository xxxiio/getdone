# Iteration 1.0.0-rc.1: Rollout Readiness

## Why this was the highest-priority next step

All planned capability milestones were complete in 0.9.0. The remaining risk was adoption, not a
missing feature. This iteration therefore added no workflow family, language, adapter category,
registry concept, or prompt-generation layer.

## Delivered

- Three executable dogfood cases across feature, bug-fix, and refactoring work.
- Python and C++ project ecosystems.
- Codex, Claude, and Cursor adapter delivery paths.
- A frozen v1 public-contract manifest and validator.
- A ten-minute recommended adoption path.
- A Python 3.11–3.13 and Ubuntu/macOS/Windows CI matrix configuration.
- A schema-backed committed rollout report.

## Evidence

Each case validates the baseline state, bootstraps project-owned `.agent/` state, verifies the
composition lock, installs or resolves its adapter, selects minimum task context, applies the
reviewed solution, runs project tests, and validates the completed project. The rollout matrix is
reproducible with:

```bash
python getdone/rollout_validation.py --repository-root . --check
```

## Health results

- Repository, front-matter, registry-index, public-contract, benchmark, and rollout validation pass.
- 107 tests pass.
- All 13 frozen console entry points pass from the built wheel.
- The three-case rollout matrix passes across Python and C++.
- Changed Python code satisfies the 100-column and 50-line function review triggers.

## Limitations

This environment cannot publish to an authorised remote, run the remote-hosted macOS/Windows and
alternate-Python jobs, sign the tag, or independently invoke vendor coding models. The RC is therefore local, annotated, and unsigned. Adapter contracts and
project files are exercised, but independent vendor-model behaviour remains external evidence.

## Internal-testing readiness

The repository is ready for internal rollout: packaged tooling is runnable, core smoke workflows
pass, project-owned files are protected, composition is reproducible, and no known blocking
state-loss issue exists.

## Next deterministic step

Run the RC in real internal repositories and accept only rollout-blocking fixes. Publish v1.0 after
an authorised remote and signing process are available and the RC produces no blocking findings.
